# Owner checklist — publishing only after separate approval

**This file records the original repository setup and subsequent maintainer-update controls.** The public GitHub repository already exists; this task changes only an isolated local feature branch. It makes no app change, push, or deployment. Keep private Tendo entirely separate.

## Public repository metadata

- **Name:** `tendo-translations`
- **Description:** Help Tendo speak your language. Improve translations, contribute new languages, and make Tendo feel at home worldwide.
- **Topics:** `tendo`, `localization`, `translations`, `ios`, `watchos`, `swiftui`, `xcstrings`, `community`, `productivity`
- **Default branch:** `main`, after the approved PR is reviewed and merged
- **Wiki/Projects/Discussions:** leave disabled initially; use Issues + PRs
- **Issues:** enabled; three Issue forms are included
- **Actions:** read-only validation workflow; do not add repository secrets

## Pre-publication owner actions

1. Review the complete public ZIP, initial commit, all strings and documents. Resolve any accidental disclosure before uploading; deletion from a public history is not sufficient containment.
2. Create an empty repository **only with separate approval**. Do not initialize it with GitHub's autogenerated README/license/gitignore because this package already includes them and you want to avoid accidental divergent histories.
3. Configure **Rulesets/branch protection** for `main` only after both PR checks have passed on real GitHub PRs: PR required, `validate-public-catalogs` and `trusted-pr-scope` required, conversation resolution, force pushes off, branch deletion off, and bypass disabled. Require an independent approval where available; if working alone, do not configure a required review that cannot be obtained. Prefer strict status checks after the green-PR proof. Restrict expected status-check source to GitHub Actions where supported.
4. Set up **CODEOWNERS** only once the real GitHub handle is confirmed (do not use placeholder or guessed accounts). Protect docs, baseline, tools, workflow and licensing files from unreviewed changes, and ideally all language files. A maintainer-only review is essential even with CI.
5. Enable private vulnerability reporting where available, and configure an authentic support contact through your official channels. `SECURITY.md` intentionally includes no unverified email.
6. Once the repository is public, test all three Issue forms through **Issues → New issue** and confirm Actions permissions are **read-only** at workflow level. Review Actions settings for outside-contributor approval policies.
7. Publish the read-only validation check first; never add private Tendo access tokens, signing credentials, or deploy workflows to this public repository.
8. The ordinary PR validator uses the trusted read-only PR policy to accept a single-language
   catalog submission or a bounded owner-authored maintainer PR. The **separate, immutable-base
   PR path guard** prevents contributor workflow tampering. The guard runs on `pull_request_target`
   but only inspects GitHub API metadata: it never checks out, imports or executes fork code, and
   has only read permissions. After both checks pass on real PRs, require `validate-public-catalogs`
   and `trusted-pr-scope` from GitHub Actions; a manually dispatched run cannot substitute for
   either required PR check. **Before** making `trusted-pr-scope` required, inspect the repository's
   Actions event policy and verify that `pull_request_target` remains permitted: GitHub announced
   a default block for this event in public repositories effective December 2, 2026. If the event
   is blocked, approve a safe alternative before enabling protection. Community PRs stay restricted
   to one language; only authenticated owner PRs from the same repository receive a bounded
   maintainer allowlist. Catalogs, export baseline, review batch definitions and source-provenance
   protections remain unchanged. Any bootstrap maintainer exception must be documented,
   separately approved and verified manually; never call a red check green.

## Contribution and release decisions

Review and merge translation PRs into the **public repository** only after technical/human review. A reviewed public PR does **not** change the private Tendo application. Use offline private-import dry-run against your latest authoritative app repository and seek the usual separate Tendo implementation, testing, Git, TestFlight and release approvals.

See the **separate delivery handoff outside this public repository** for exact verified local ZIP extraction and initial remote-setup commands.

## Subsequent AI-draft bulk export (maintainer-controlled)

The complete AI-draft update is developed on a dedicated task branch and **does not get published automatically**. It changes all seven language packs and protected scripts, export hashes, batch manifests and documentation. The standard `validate-public-catalogs` workflow **intentionally rejects** such a multi-language PR, including when its author is the owner; this guard must never be weakened to make routine contributions easier.

Before separately authorizing any push/PR/merge, verify the branch and public-content screening, run the offline tests, validate all 21 catalogs and the review ledger, and use the read-only `verify_maintainer_export.py --repo <owner-branch> --previous <clean-main>` check. An optional **owner-triggered** GitHub Actions `Owner-controlled AI export verification` workflow is limited to `DrRoglaa` and has read-only permissions. It runs only after the owner manually dispatches it on the reviewed owner-controlled branch. This extra workflow **does not bypass branch protection** or change the default PR validator.

For the **first** bulk-update PR, GitHub cannot manually dispatch a newly added workflow before that workflow exists on the default branch. Perform the identical validation locally on the independently reviewed maintainer checkout and retain its logs. The optional owner-dispatched workflow is for **subsequent** updates, once this workflow is present on `main`. For the one-time maintainer PR, follow the repository's actual ruleset: obtain explicit permission for a **documented temporary maintainer exception** to the standard one-locale required check (if that check is mandatory), independently review the complete diff and read-only verification results, then restore protections immediately. Do not push to or merge into protected `main` until separate approval. If no safe exception is available, STOP and agree on a different rollout. Never use a fork-supplied script as the privileged maintainer export validator.

The `review/languages/*.json` approvals are maintained **only after genuine independent sign-off** and verifiable public evidence. A successful bulk export does not grant any language review or app release status.
